# 개발 규칙

하나의 변경은 사용자 동작이나 결함 하나를 구현하고 검증할 수 있는 범위로 정합니다. 파일별로 작업을 쪼개거나 독립 기능을 같은 변경에 계속 추가하지 않습니다. 에이전트 진입점은 [AGENTS.md](../AGENTS.md)입니다.

## 작업과 Git

기능 개발과 결함 수정은 이슈·브랜치·PR로 추적합니다. 외부 게시가 승인된 작업에서 이슈를 만들고, 로컬 감사·문서 수정만 요청받았다면 그 결과를 먼저 완성합니다. 절차를 이유로 새 게시 권한을 추정하지 않습니다.

기본 브랜치는 `main`입니다. 첫 커밋과 최초 push 전에 브랜치명을 확인하며, `master`로 초기화되어 있으면 `main`으로 변경합니다. 최초 push는 `git push -u origin main`으로 대상을 명시하고 원격 기본 브랜치도 확인합니다.

작업 브랜치는 `codex/<issue>-<short-slug>` 형식을 사용합니다. 이슈가 없는 로컬 작업은 번호를 생략합니다. 독립 작업의 워크트리는 저장소 밖에 두고 기존 워크트리에 중첩하지 않습니다. 같은 폴더에서 여러 에이전트가 동시에 수정하지 않습니다.

커밋은 `type: 한국어 변경 설명`으로 씁니다. 타입은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`, `perf`, `style`, `revert`를 사용합니다. 관련 이슈가 있으면 제목 끝에 `(#번호)`를 붙일 수 있습니다. 본문은 변경 이유와 영향이 제목만으로 드러나지 않을 때 씁니다.

```text
fix: 물 높이를 바꾼 뒤에도 넘침 기록 유지
docs: 센서 권한과 체험 모드 안내 보완
```

이번 작업의 경로만 명시해서 stage합니다. `git add .`와 `git add -A`, 다른 작업의 reset·clean·stash, 승인하지 않은 이력 재작성을 하지 않습니다. 새 커밋을 추가하면 그 변경에 영향을 받는 검증을 다시 실행합니다.

PR에는 문제, 바뀐 동작, 실제 검증과 남은 한계를 적습니다. 완료 조건이 남은 PR은 Draft로 유지합니다. 리뷰 의견은 근거를 확인한 뒤 반영하거나 이유를 설명합니다. 병합은 승인 범위, 현재 head의 검사 결과, 미해결 결함을 확인한 뒤 진행합니다. 게시·병합·배포는 서로 다른 결과로 보고합니다.

## 코드와 테스트

TypeScript의 `strict`와 현재 타입 검사 옵션을 유지합니다. UTF-8(BOM 없음), LF, 들여쓰기 2칸을 사용합니다. 코드 식별자·API·로그 원문은 보존하고 설명은 한국어로 작성합니다.

`src/core/`는 DOM, `window`, `navigator`, `performance`를 사용하지 않습니다. 시간과 센서 입력은 인자로 받습니다. 물리 계산을 바꾸면 관련 회귀 테스트로 확인하고, UI 변경은 실제 이벤트와 상태 전이까지 확인합니다.

검증 명령과 각 검사의 범위는 [개발 안내](DEVELOPMENT.md)에 있습니다. 작은 문서 변경에 전체 테스트를 일괄 강제하지 않습니다. 보안 검사·빌드 설정을 바꾸면 우회 입력과 배포 결과도 확인합니다. 통과 이후에는 새 변경·실패·미해결 우려가 있을 때만 검증을 늘립니다.

## 문서와 글쓰기

README는 사용 안내, DEVELOPMENT는 실행·검증, TECHNICAL은 구현과 한계를 설명합니다. 같은 규칙을 여러 문서에 복사하기보다 해당 문서를 연결합니다.

한국어 문서는 합니다체로 씁니다. 독자가 필요한 사실과 행동을 먼저 설명하고, 상투적 도입·칭찬·완료 선언·반복 요약을 덜어냅니다. 문장을 줄이면서 원인, 수치, 예외, 미검증 사항을 삭제하지 않습니다.

문장을 추가할 때는 이 문서의 독자가 지금 알아야 할 내용인지 확인합니다. 요청하지 않은 제품 평가, 면책 문구, 가상의 위험에 대한 경고를 예방적으로 덧붙이지 않습니다. 제품을 임의로 시제품이라 규정하거나 용도·성능·책임 범위를 먼저 단정하지 않습니다.

README에는 앱 소개와 사용에 필요한 설명을 둡니다. 실제로 확인한 결함·검증 범위는 기술 문서나 작업 기록에서 다루고, 별도 논의가 필요한 정책을 사용 안내에 끼워 넣지 않습니다. 이미 충분한 설명에는 주의 문구나 같은 뜻의 요약을 덧붙이지 않습니다.

기존 글의 시점과 검증 주체를 보존합니다. 사실 오류를 정정할 때는 이유와 근거를 남기고, 문체 편집을 이유로 과거 미완료 작업을 완료로 바꾸지 않습니다. 원본 백업은 저장소 밖에 보관합니다.

## 데이터 처리

센서 데이터의 수집·저장·전송 방식을 바꿀 때는 데이터 항목과 사용 목적을 함께 설명합니다. 실제 사용자 데이터를 코드·문서·테스트에 포함하지 않습니다.
